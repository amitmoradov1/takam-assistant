# תכ"ם-קל — שאלות ותשובות מעוגנות-מקור מעל הוראות התכ"ם

**תכ"ם-קל** הוא POC של עוזר צ'אט שמאפשר לעובדי מדינה לשאול שאלה בשפה
חופשית על הוראות התקנון הכספי והמשקי (תכ"ם) ולקבל תשובה תמציתית בעברית,
**עם הפניה מדויקת להוראה, לסעיף ולנספח** שעליהם היא מבוססת. המערכת עובדת
על מדגם של 8 הוראות אמיתיות שנאספו מאתר התכ"ם (פרק "התקשרויות ורכישות"),
והממשק מעוצב בהשראת השפה העיצובית של שירותים ממשלתיים דיגיטליים (RTL מלא).

---

## חלק א': זיהוי בעיה ותכנון פתרון

### הבעיה

אתר הוראות התכ"ם הוא המקור המחייב למדיניות הכספית והמשקית של הממשלה, אבל
האופן שבו המידע מוגש בו מקשה על המשתמש התפעולי:

1. **המידע בנוי כמסמכים משפטיים, לא כתשובות.** עובד רכש שצריך לדעת "עד
   איזה סכום מותר לבצע רכש בהליך מקוצר?" נדרש לדעת מראש *באיזו הוראה* זה
   כתוב (7.7.1? 7.6.1?), להוריד קובץ Word ארוך ולאתר את הסעיף בעצמו.
2. **המידע מפוזר.** תשובה מעשית אחת (למשל: התקשרות עם ספק יחיד) נשענת
   לעיתים על כמה הוראות, על תקנות חובת המכרזים ועל נספחים — אין מקום אחד
   שמרכז אותה.
3. **חיפוש מילולי נחלש בעברית.** חיפוש "התקשרות בפטור" לא ימצא בהכרח
   "ההתקשרויות הפטורות" — הטיות ותחיליות שוברות התאמת מילות מפתח.
4. **עלות הטעות גבוהה.** פרשנות שגויה של סעיף פירושה פגם בהליך מכרזי,
   חריגה מסמכות או ליקוי ביקורת. בפועל השאלות האלה מגיעות לרפרנטים
   ולחשבים — צוואר בקבוק אנושי לשאלות שרובן חוזרות על עצמן.

**מדוע כדאי לפתור את זה:** קהל היעד הוא כל גורמי הרכש, הכספים ומשאבי האנוש
במשרדי הממשלה. קיצור זמן מענה מ"חיפוש של חצי שעה או מייל לרפרנט" ל"תשובה
מצוטטת בשניות" חוסך זמן עבודה רב, מקטין טעויות ציות, ומפנה את המומחים
לשאלות הקשות באמת.

### הפתרון

**צ'אט שאלות-תשובות מבוסס RAG (Retrieval-Augmented Generation):**

1. המשתמש שואל שאלה בשפה חופשית.
2. מנוע אחזור מותאם-עברית שולף את הסעיפים הרלוונטיים ביותר מתוך מאגר
   ההוראות שנאסף מהאתר.
3. מודל שפה (Claude) מנסח תשובה **אך ורק מתוך הסעיפים שנשלפו**, עם ציטוט
   לכל קביעה: `[מקור 1] הוראה 7.7.1, סעיף 2.1`, ושני קישורים לכל מקור:
   לעמוד ההוראה באתר ולקובץ ה-Word המחייב עצמו (הורדה ישירה מהאתר —
   עובד תמיד, בלי תלות בניתוב ה-SPA של האתר).
4. אם אין במקורות תשובה — המערכת אומרת זאת במפורש במקום לנחש.

הבחירה ב-RAG (ולא "לשאול מודל שפה ישירות") היא מהותית בהקשר רגולטורי:
היא מעגנת כל תשובה בנוסח ההוראה עצמו, מקטינה הזיות, ומאפשרת למשתמש לאמת
את התשובה בלחיצה — התשובה היא *מפה אל ההוראה*, לא תחליף לה.

### התכנון הטכני

```
                 ┌───────────────── שלב אופליין (אינדוקס) ─────────────────┐
API אתר התכ"ם ──► scraper ──► DOCX ──► שחזור מספור ──► פירוק לסעיפים ──► אינדקס BM25
 (מטא-דאטה,     (data/raw)         (docx_extract.py)   ונספחים          + גרף הפניות
  גרסאות, קבצים)                                       (parsing.py)      (index.py)

                 ┌───────────────── שלב אונליין (שאילתה) ─────────────────┐
שאלת משתמש ──► FastAPI ──► אחזור top-k קטעים ──► Claude API ──► תשובה + ציטוטים ──► UI
              (api.py)      (index.py)           (llm.py)           (web/)
```

| רכיב | מימוש | למה דווקא כך |
|---|---|---|
| איסוף נתונים | `scraper.py` — ה-API הפנימי של אתר התכ"ם (מטא-דאטה ← גרסה מפורסמת אחרונה ← קובץ DOCX), עם fallback גנרי ל-HTML/PDF/DOCX מכל URL | האתר הוא SPA ‏(Angular) — ה-HTML ריק ו-scraping קלאסי לא עובד. מיפוי ה-API (דרך קריאות הרשת של האתר) נותן מקור מובנה: כותרת, פרק, תאריך תחולה ומספר גרסה אמיתיים במקום ניחוש |
| חילוץ טקסט | `docx_extract.py` — פענוח DOCX ‏(stdlib בלבד) כולל **שחזור מספור הסעיפים האוטומטי של Word** מתוך numbering.xml/styles.xml | מספרי הסעיפים — הבסיס לכל ציטוט — אינם קיימים כטקסט בקובץ; הם מספור אוטומטי. בלי השחזור אין "סעיף 2.3.1", ואיתו הציטוט מגיע מאומת עד רמת תת-סעיף ונספח |
| פירוק וחלוקה | פירוק לפי המספור ההיררכי + זיהוי נספחים (המספור בהם מתחיל מחדש ← "נספח ג, סעיף 2"); כל קטע נושא פירורי-לחם של כותרות האב | זה מה שמאפשר ציטוט ברמת סעיף, וכותרות האב ("עדיפות המכרז הפומבי") נושאות את מילות ההקשר שסעיף-משפט בודד לא מכיל |
| אחזור | BM25 בכתיבה עצמית + נרמול עברי (ניקוד, אותיות סופיות, תחיליות) + אינדוקס כותרת ההוראה + בוסט לזיהוי מספרי הוראה בשאלה + משקל מופחת לקטעי רשימות-הפניה | אפס תלויות חיצוניות, דטרמיניסטי, ניתן לבדיקה ביחידות, ועובד גם ברשת סגורה. כל אחת מההתאמות נמדדה מול סט הזהב (ראו "בדיקות"). שדרוג ל-hybrid מתואר בחלק ג' |
| גרף הפניות צולבות | חילוץ אוטומטי של 'בהתאם להוראת תכ"ם, "שם", מס\' X' ← גרף דו-כיווני ← "הוראות קשורות" בכל תשובה | הוראות תכ"ם מפנות זו לזו באופן שיטתי; ההפניות הן ידע דומיין: "מה עוד כדאי לקרוא". דיוק לפני כיסוי — רק מספרים בהקשר "הוראה"/"מס'", לא מספור סעיפים פנימי |
| יצירת תשובה | Claude ‏(`claude-sonnet-5`, איזון איכות/עלות; `TAKAM_MODEL=claude-opus-5` לאיכות מרבית) עם system prompt שמחייב עיגון וציטוט; כל תשובה נפתחת ב**"שורה תחתונה"** — הסקה ישירה לשאלה שנשאלה (מוצגת כקופסה מובלטת), עם בלמים: הסקה רק מהמקורות, ציטוט גם עליה, ופרט חסר מנוסח כתנאי; שאלה מחוץ לתחום מזוהה כמצב נפרד (llm_no_answer) שבו ה-UI לא מציג מקורות לא רלוונטיים; fallback למצב "אחזור בלבד" בכל כשל API | בדומיין רגולטורי המשתמש צריך גם את המסקנה המעשית וגם את היכולת לאמת אותה; הפרדת שכבת ה-LLM מאחורי ממשק אחד (`llm.py`) מאפשרת החלפת מודל/ספק בשינוי קובץ אחד |
| שרת + UI | FastAPI + עמוד HTML יחיד ב-RTL, ללא פונטים/ספריות מ-CDN; תפריט צד לניהול שיחות (שיחה חדשה, מעבר, מחיקה) שנשמר ב-localStorage של הדפדפן בלבד ומשוחזר בטעינה | מינימום הנדרש לממשק שמיש; עמוד עצמאי שמכבד את ה-CSP שלו ועובד גם ברשת סגורה. ההיסטוריה בצד הלקוח בכוונה — השרת לא שומר תוכן שאלות (פרטיות) |
| רב-לשוניות | מתג שפה עברית/אנגלית בממשק (כולל היפוך RTL/LTR, נשמר בדפדפן); **שפת הממשק קובעת את שפת התשובה** (וגם מבדלת את ה-cache); שאלה ללא עברית מתורגמת אוטומטית לעברית (קריאת LLM קצרה) **לצורך האחזור בלבד** — האינדקס הלקסיקלי עברי | מאפשר לשאול באנגלית בלי לבנות אינדקס דו-לשוני; הציטוטים ומספרי ההוראות נשארים בעברית כי הנוסח המחייב עברי. בלי מפתח API הגשר כבוי בחן |
| בדיקות | pytest ‏(65) — נרמול, חילוץ DOCX, פירוק, אחזור, הפניות, API, הקשחה, סקריפט ההרצה | מכסות את הליבה הדטרמיניסטית; שכבת ה-LLM מבודדת כך שהבדיקות לא תלויות ברשת |

## חלק ב': הרצת ה-POC

### התקנה והרצה (2 פקודות)

```bash
pip install -r requirements.txt
python scripts/run.py                  # בדיקת מוכנות + בניית אינדקס + הרצה
```

ואז לגלוש אל http://127.0.0.1:8000

`run.py` מוודא לפני ההרצה שהכול במקום — גרסת Python, תלויות, נתונים,
אינדקס עדכני (נבנה אוטומטית אם חסר), מפתח API ופורט פנוי — ומדווח
בצ'ק-ליסט ברור (`--check-only` לבדיקה בלבד). לחלופין, הרצה ידנית:
`python scripts/build_index.py` ואז
`uvicorn takam_assistant.api:app --app-dir src --reload`.

**חיבור מודל השפה (מומלץ):** שימו את המפתח ב-`.env` (ראו `.env.example`) —
`run.py` טוען אותו אוטומטית. בלי הקובץ: `export ANTHROPIC_API_KEY=sk-ant-...`

בלי מפתח, המערכת עובדת במצב "אחזור בלבד" — מציגה את הסעיפים הרלוונטיים
במקום תשובה מנוסחת. זהו גם ה-fallback האוטומטי לכל כשל API (רשת, אימות,
rate limit) — המערכת לעולם לא מחזירה 500 בגלל ה-LLM.

**שאילתה מהטרמינל בלי שרת:**

```bash
python scripts/ask.py "מהי תקרת הסכום להתקשרות בהליך רכש מקוצר?"
```

### מדגם הנתונים (data/raw)

בהתאם להמלצת המטלה ("להתמקד בתחום מסוים ולהימנע מהיקף נתונים גדול"),
המדגם — שנאסף מהאתר ומצורף ל-repo — כולל 8 הוראות מפרק **"התקשרויות
ורכישות"** שנבחרו לכסות מחזור חיים של התקשרות, עם הפניות צולבות ביניהן:

7.1.1 ועדות מכרזים · 7.2.3 פנייה מוקדמת (RFI) · 7.3.3 ערבויות וביטחונות ·
7.4.1 ניהול ההליך המכרזי · 7.6.1 פטור מחובת המכרז · 7.7.1 התקשרות בהליך
מקוצר · 7.7.4 התקשרות עם בעל מקצוע מומחה · 7.13.1 מאגר מציעים

להרחבת המדגם: מוסיפים מספרי הוראות ל-`data/sources.txt` ומריצים:

```bash
python -m takam_assistant.scraper data/sources.txt
python scripts/build_index.py
```

האיסוף אינקרמנטלי (מניפסט זוכר מה כבר נאסף; הרצה חוזרת מורידה רק חדשות),
עמיד לכשלים (3 ניסיונות למקור, כשל בודד לא עוצר את השאר), ומנומס (השהיה
בין בקשות). כל מסמך נשמר עם גרסתו (`version`) — הבסיס לזיהוי עדכוני
הוראות ב-production. `data/sample/` מכיל בנוסף מסמכי דוגמה סינתטיים
קטנים המשמשים את בדיקות היחידה (דטרמיניסטיים ואינם תלויים באיסוף).

אף שהמדגם ממוקד, הארכיטקטורה נמדדה גם בסדר הגודל של כלל התכ"ם: בניית
האינדקס הנוכחי (960 קטעים) אורכת פחות משנייה וחיפוש ~5ms לשאילתה —
הרחבת הכיסוי היא עניין של נתונים בלבד, לא של קוד.

### בדיקות והערכת איכות

```bash
python -m pytest tests/ -v          # 65 בדיקות יחידה ואינטגרציה
python scripts/eval_retrieval.py    # הערכת אחזור מול סט שאלות זהב אמיתי
```

הבדיקות מכסות: נרמול עברי (תחיליות, אותיות סופיות), חילוץ DOCX עם שחזור
מספור (על קובץ שנבנה בזיכרון), פירוק היררכי כולל נספחים, חלוקה לקטעים עם
מטא-דאטה לציטוט, דיוק אחזור (כולל בוסט למספרי הוראה), חילוץ הפניות בשני
סגנונות הכתיבה, API מקצה לקצה (במצב דטרמיניסטי, ללא תלות ברשת או במפתח),
ושכבת התפעול: rate limiting, כותרות אבטחה, ניקוי קלט, מדדים, משוב ו-cache.

**הערכת אחזור שיטתית:** `data/eval/gold.json` מחזיק 16 שאלות זהב שנכתבו
מול המדגם האמיתי, ו-`eval_retrieval.py` מודד recall@1 / recall@5 / MRR.
תוצאות נוכחיות: **recall@5 ‏100%, recall@1 ‏81%, MRR ‏0.906**, ו-CI אוכף
רף מינימלי (recall@5 ≥ 0.9). ה-eval הזה הוכיח את עצמו פעמיים בפיתוח:

1. על הנתונים הסינתטיים — קטע-הפניה זעיר שגנב את המקום הראשון (פתולוגיית
   BM25 על קטעים קצרים) ← תוקן ברצפת אורך אפקטיבי.
2. על הנתונים האמיתיים — recall@1 פתח ב-62.5%: סעיפי "מסמכים ישימים"
   (רשימות שמצטטות את כותרות ההוראות האחרות) התחזו לתשובות, ושאלות
   המנוסחות במילות כותרת ההוראה ("בעל מקצוע מומחה") פוספסו ← תוקן במשקל
   מופחת לקטעי רשימות-הפניה ובאינדוקס כותרת ההוראה לכל קטע, ונמדד שוב.

**מגבלות מוצהרות:** איכות הניסוח של ה-LLM עצמה אינה נמדדת אוטומטית ב-POC
(המשוב שנאסף ב-`/api/feedback` הוא התשתית לסט כזה); טבלאות במסמכי Word
נשטחות לרצף שורות (התוכן נשמר, המבנה לא); ושלוש שאלות זהב שבהן ההוראה
הנכונה מדורגת שנייה ולא ראשונה — ביטוי לגבול של אחזור לקסיקלי, שעליו עונה
השדרוג ההיברידי בחלק ג'.

### הרצה ב-Docker

```bash
docker build -t takam-assistant .
docker run -p 8000:8000 -e ANTHROPIC_API_KEY=sk-ant-... takam-assistant
```

האימג' רץ כמשתמש לא-מורשה, והמפתח מוזרק בזמן ריצה — לא נאפה לאימג'.
`.github/workflows/ci.yml` מריץ בכל push את הבדיקות ואת שער איכות האחזור.

## חלק ג': חשיבה הנדסית והתאמה ל-Production

### שיקולים שהנחו אותי בתכנון ובחלוקה לרכיבים

- **עיגון לפני רהיטות.** בתחום רגולטורי, תשובה שגויה ומשכנעת גרועה מאין
  תשובה. לכן: ה-LLM מקבל אך ורק את הקטעים שאוחזרו, מחויב לציטוט פר-קביעה,
  ומונחה לומר "לא נמצא במקורות" — וה-UI מציג תמיד את קטעי המקור והקישור
  לנוסח המחייב.
- **הפרדה חדה בין שכבות.** `scraper → docx_extract → parsing → chunking →
  index → llm → api`: כל רכיב עם קלט/פלט מוגדרים, כך שכל אחד ניתן להחלפה
  (אחזור אחר, מודל אחר, UI אחר) בלי לגעת בשאר. זו גם הסיבה שהבדיקות פשוטות.
- **הליבה דטרמיניסטית, ה-LLM בקצה.** כל מה שאפשר לבדוק ביחידות (חילוץ,
  פירוק, אחזור) לא תלוי במודל; המערכת שמישה גם כשה-LLM לא זמין (graceful
  degradation), וזה גם מה שהופך את הדמו לאמין.
- **המטא-דאטה היא המוצר.** ההשקעה המרכזית היא בשחזור מבנה הסעיפים
  והנספחים מקובצי ה-Word — בלעדיה אין ציטוט מדויק, ואיתה גם אחזור פשוט
  נהיה מועיל.
- **תפירה לעברית ולדומיין.** נרמול תחיליות ואותיות סופיות, זיהוי מספרי
  הוראה בשאלה ("מה קובעת 7.7.1?"), והיכרות עם מבנה ההוראה (נספחים,
  "מסמכים ישימים") — התאמות קטנות שכל אחת מהן נמדדה ושינתה מהותית את
  איכות האחזור.

### מה כבר מיושם ב-POC מעבר למינימום (שכבת תפעול ואבטחה)

| תחום | מה מיושם | איפה |
|---|---|---|
| לוגים | לוגים מובנים JSON (שורה לאירוע) עם request_id לכל בקשה, latency, ציוני אחזור ושימוש בטוקנים — מוכנים לשאיבה ל-ELK/Loki. פרטיות: תוכן שאלות לא נרשם כברירת מחדל (רק fingerprint), כי שאלות עובדים עלולות להכיל מידע רגיש | `observability.py` |
| ניטור | `/api/metrics`: מוני בקשות/שגיאות/מצבי תשובה, שימוש בטוקנים (עלות!), ו-latency ממוצע ו-p95 | `observability.py` |
| אבטחה | Rate limiting פר IP (חלון הזזה), כותרות אבטחה (CSP, nosniff, frame-ancestors), ניקוי תווי בקרה מהקלט, escaping מלא ב-UI | `security.py` |
| prompt-injection | קטעי מקור תחומים בתגיות `<source>` + הנחיה מפורשת למודל להתייחס לתוכנם כנתונים בלבד — מסמך שנאסף מהאינטרנט לא יכול "לפקד" על המודל | `llm.py` |
| עמידות ועלות | Cache LRU לתשובות (מפתח כולל את זהות הקטעים — עדכון אינדקס מפקיע אוטומטית), fallback אוטומטי למצב אחזור בכל כשל API, רישום טוקנים פר קריאה | `llm.py` |
| משוב | `/api/feedback` + כפתורי 👍/👎 ב-UI, נשמר ל-JSONL — בקרת איכות ומקור לשאלות eval. (בניגוד ללוגים, המשוב כן שומר את נוסח השאלה — זו מסירה יזומה של המשתמש לצורך שיפור, והקובץ נשמר מקומית בלבד) | `api.py` |
| הערכת איכות | סט שאלות זהב אמיתי + recall@1/recall@5/MRR, עם שער איכות ב-CI | `scripts/eval_retrieval.py` |
| פריסה | Dockerfile (משתמש לא-מורשה, secrets בזמן ריצה) + GitHub Actions CI | `Dockerfile`, `.github/` |

החלטות מודעות על מה **לא** נכנס ל-POC: אימות משתמשים (יגיע מ-SSO ארגוני/הזדהות
ממשלתית, לא ממימוש עצמי), Prometheus/Grafana (המדדים חשופים ב-endpoint והמעבר
הוא טכני), ו-Redis ל-rate limiting מבוזר (נדרש רק במספר שרתים).

### מה הייתי משנה כדי להפוך את הפתרון למערכת Production

1. **צנרת נתונים מנוהלת במקום איסוף ידני:** ה-API של האתר כבר חושף מספרי
   גרסה ותאריכי תחולה (נשמרים היום עם כל מסמך) — ב-production: סריקה
   מתוזמנת של כל ההוראות, אינדוקס מחדש אוטומטי כשמספר הגרסה עולה, וסימון
   למשתמש "ההוראה עודכנה בתאריך X". אידיאלית: הסדרת גישה רשמית ל-API מול
   מנהלי האתר במקום הסתמכות על ממשק פנימי.
2. **אחזור היברידי:** BM25 + embeddings רב-לשוניים (מודל שניתן להריץ
   מקומית) עם reranking, נמדד מול סט הזהב הקיים לפני החלפה — זה המענה
   לשאלות שמנוסחות רחוק מניסוח ההוראה.
3. **הרחבת ה-evals לאיכות התשובה:** סט שאלות-תשובות מאושר ע"י רפרנט מקצועי
   (מוזן מהמשוב שכבר נאסף), הרצה אוטומטית בכל שינוי prompt/מודל, ומדדים:
   נאמנות למקור, כיסוי, אחוז "לא נמצא" מוצדק.
4. **חילוץ טבלאות:** טבלאות מדרג האישורים הן מהתוכן החשוב בהוראות; חילוץ
   מבני שלהן (שורה = תקנה + גורם מאשר) ישפר תשובות על שאלות "מי מאשר".
5. **תשתית ארגונית:** אימות משתמשים מול SSO/הזדהות ממשלתית, Prometheus/
   Grafana על בסיס המדדים הקיימים, rate limiting מבוזר (Redis), ו-alerting
   על שיעור שגיאות/עלות טוקנים.
6. **ממשק:** היסטוריית שיחה והקשר רב-תורי, streaming לתשובות, הצגת diff בין
   גרסאות הוראה, והנגשה (WCAG) כנדרש מאתר ממשלתי.

### בהנחה שנדרש לפעול בסביבה ממשלתית ללא גישה לשירותי AI חיצוניים

הארכיטקטורה תוכננה מראש לתרחיש הזה, ולכן ההתאמות ממוקדות:

- **שכבת האחזור כבר עצמאית לחלוטין** — BM25 בכתיבה עצמית, ללא קריאות רשת.
  מצב "אחזור בלבד" הקיים הוא בפועל המערכת המינימלית שעובדת באוויר סגור
  (גם ה-UI לא טוען שום משאב חיצוני).
- **החלפת ה-LLM במודל מקומי:** `llm.py` הוא נקודת ההחלפה היחידה. בסביבה
  סגורה הייתי פורס מודל פתוח בשרת פנימי — למשל מודלים פתוחים עם יכולת
  עברית סבירה (Mistral, Llama, Gemma, או מודל עברי ייעודי כדוגמת
  DictaLM) מאחורי שרת inference פנימי (vLLM/Ollama) עם אותו חוזה:
  `answer_question(question, sources) → {answer, citations}`.
- **Embeddings מקומיים** (אם משדרגים לאחזור היברידי): מודלים רב-לשוניים
  בקוד פתוח (למשל משפחת multilingual-E5) שרצים על CPU/GPU מקומי.
- **האתגרים המרכזיים הצפויים:** פער איכות בעברית בין מודלים פתוחים ל-API
  מסחרי (מחייב evals לפני מעבר והשקעה ב-prompt); עלות תשתית GPU ותחזוקת
  שרת inference; עדכוני מודלים באחריותנו; והקשחת אבטחה לפי דרישות יחידת
  הסייבר הממשלתית. היתרון: ריבונות מלאה על המידע — אף שאלה של עובד מדינה
  לא יוצאת מהרשת הממשלתית.
